# ADR 0034：API 错误契约和请求追踪

## 状态

已接受(Accepted)。

## 背景

radiaTest 的 `/api/v1` 接口由 FastAPI 路由、参数校验、认证权限和各业务模块共同产生错误。
如果直接沿用框架默认 `detail` 或让各模块自行定义响应，前端需要识别多种结构，OpenAPI
也无法准确表达实际契约。未预期异常还需要一种不暴露内部实现、又能关联服务端日志的定位方式。

## 决策

- 所有 `/api/v1` JSON 错误统一使用包含 `code`、`message` 和可选 `details`
  的 `error` 信封，具体结构以平台运行时规格为准。
- `code` 使用稳定的 `snake_case` 错误码。业务模块为需要前端可靠判断的场景定义领域错误码；
  未专门定义的 HTTP 错误映射为通用错误码。
- `message` 由后端提供中文用户提示，前端直接展示，但程序逻辑只依赖 `code`。
- 参数校验错误不直接暴露 FastAPI/Pydantic 内部错误结构。
- 不保留旧 `detail` 字段，不新增 `/api/v2`；同一代码库中的前后端一次性切换。
- HTTP 状态码继续表达协议语义，错误码不替代状态码。
- 每个 `/api/v1` 请求由服务端生成唯一 `request_id`，写入 `X-Request-ID` 响应头和
  同一请求产生的服务端日志。
- 未预期异常返回固定中文提示和 `request_id`，不暴露内部异常；完整异常只写服务端日志。
- OpenAPI 定义公共错误模型，并统一声明常见错误响应；运行时响应和 OpenAPI 不允许继续使用
  两套结构。
- 当前产品只提供中文界面，隐藏前端语言切换入口；保留框架已有国际化基础设施，不做无关拆除。

## 取舍

选择错误信封而不是扁平字段，是为了让错误响应与正常业务对象边界明确，并为以后增加有限元数据
保留稳定位置。

选择领域错误码和通用错误码并存，而不是为每个端点的每种错误创建唯一编号，是为了让前端能够
可靠处理重要业务分支，同时控制错误码维护成本。

选择服务端中文消息而不是前端错误码翻译，是因为当前没有多语言需求。前端仍只依赖错误码，
以后增加多语言时可以替换展示层，不改变业务判断。

选择为所有 API 请求生成 `request_id`，而不是仅在 500 时临时生成，是为了让异常发生前的
访问日志和业务日志也能与用户看到的错误关联。

## 影响

- FastAPI 需要统一处理框架错误、参数校验错误、业务错误和未预期异常。
- 前端请求层需要统一读取错误信封，不再读取 `detail`。
- 日志格式和 OpenAPI 需要包含统一请求追踪和错误模型。
- API 错误对外行为和验收标准以平台运行时规格为准。
