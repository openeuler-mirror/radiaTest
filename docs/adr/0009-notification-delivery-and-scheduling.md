# ADR 0009：通知投递和定时提醒

## 状态

已接受。

## 背景

radiaTest 需要向用户提示资源即将到期和工单变化。通知既要在 Web 中留有稳定记录，也要在
适用场景复用现有飞书身份绑定；资源到期提醒还需要主动定时触发，不能依赖资源页面的懒释放。

## 决策

- PostgreSQL 中的站内通知是唯一事实来源；读取状态和投递状态都保存在数据库中。
- 资源到期提醒同时写入站内通知，并在用户已绑定飞书且 Bot 启用时额外发送飞书私聊卡片。
- 工单通知只进入站内通知，不投递飞书。
- 不提供邮件、短信、浏览器系统通知或用户通知偏好设置。
- 使用单张 `notifications` 表保存通知和可选的飞书投递状态，不预先拆分通用多渠道投递模型。
- 通知类型由代码枚举约束，数据库保存字符串，不使用 PostgreSQL Enum。
- 工单变更和站内通知在同一 PostgreSQL 事务中提交；飞书投递在事务提交后异步执行，失败不回滚业务。
- 飞书发送任务使用现有 Celery 和 Redis，失败最多重试 3 次。站内通知已写入但任务未成功投递时，
  不增加后台补发扫描或管理员手动重发。
- 每套 `dev` 和 `prod` 环境各运行一个 Celery Beat，按 `Asia/Shanghai` 每天 09:00 触发
  到期提醒扫描和通知清理。Beat 使用独立持久化调度文件，不能随 Worker 并发数扩容。
- Redis 只承载 Beat 到 Worker 的任务投递，不保存通知业务状态。
- 当天 09:00 停机导致定时点错过时不补跑，不增加小时扫描或启动补偿。
- 通知保留 90 天，每日到期扫描完成后清理超期通知。
- 通知创建、飞书投递、标记已读和全部已读不写入审计日志或租约日志。
- Web 不轮询通知；页面进入、路由切换或用户手动刷新时读取最新通知。
- Web 通知可以跳转工单或资源详情；飞书资源提醒只进入现有资源卡片，不跳转 Web。

## 原因

站内通知作为事实来源可以避免飞书故障造成信息永久丢失。复用 Celery/Redis 和新增单个 Beat
进程，比系统 cron 或自研调度线程更符合现有异步执行模型。单表足以覆盖当前站内和飞书两个
明确渠道，避免为尚未需要的邮件等渠道引入投递抽象。

## 影响

- 数据库新增通知表和对应迁移。
- 后端新增通知查询、已读操作、到期扫描和飞书投递任务。
- 前端顶部增加通知铃铛和通知抽屉。
- 部署拓扑新增每套环境唯一的 Celery Beat 服务及其调度文件命名卷。
- 通知收件人、去重、正文和页面行为以通知功能规格为准。
