# 通知管理规格

## 状态

有效(Active)。

## 目标

radiaTest 提供持久化站内通知，并在资源即将到期时按条件补充飞书提醒。通知用于告知用户，
不替代工单、租约、审计日志或任务事件。

## 通知模型

- 每条通知只属于一个接收人，其他用户和管理员不能查看。
- 通知保存类型、标题、正文、目标类型、目标 ID、站内相对跳转地址、读取时间、创建时间、
  去重键，以及可选的飞书投递状态、失败原因和投递时间。
- 通知类型由代码枚举约束，数据库保存字符串。
- 支持的通知类型为：
  - `lease.expiring`
  - `ticket.commented`
  - `ticket.assigned`
  - `ticket.reassigned`
  - `ticket.rejected`
  - `ticket.completed`
  - `ticket.updated`
- 同一次业务操作对同一接收人最多创建一条通知，正文汇总本次变化。
- 工单一次修改包含多种变化时，通知类型按责任人变化、状态变化、普通处理字段变化的顺序
  选择主要类型。
- 去重键必须唯一。工单通知按业务操作和接收人去重；到期提醒按租约 ID、当前到期时间、
  提醒日期和接收人去重。
- 通知不支持用户删除，创建 90 天后由每日任务统一清理，已读和未读使用相同保留期。

## 资源到期提醒

- 有期限的物理机和 VM 租约分别在到期日的前 3、前 2 和前 1 个自然日提醒。
- 每天 09:00 按 `Asia/Shanghai` 扫描一次，同一天重复执行不能重复创建通知。
- 当天 09:00 后新建或修改且已经进入三天窗口的租约，从下一次 09:00 开始提醒，不补发
  已错过的提醒。
- 永久租约、已释放租约和已经到期的租约不生成即将到期提醒。
- 接收人只包括当前租约所有者，不因管理员角色额外抄送。
- 续期不会撤回或改写已有通知；后续扫描按最新到期时间重新计算。
- 提前释放物理机或销毁 VM 后不再生成后续提醒。
- 到期通知正文包含资源类型、物理机 OS IP 或 VM 名称、到期时间和剩余天数，不包含凭据。
- 到期提醒写入站内通知。接收人已绑定飞书且当前环境 Bot 已启用时，再投递飞书私聊卡片。
- 飞书卡片可以进入现有物理机或 VM 详情卡片，不包含 Web 链接。

## 工单通知

- 新增评论时通知工单提出人和当前责任人。
- 接受并指派工单时通知提出人和责任人。
- 重新指派时通知提出人、原责任人和新责任人。
- 拒绝、完成、修改优先级或修改计划完成时间时只通知提出人。
- 所有场景都排除本次操作人本人，并对重复接收人去重。
- 同一次处理操作同时修改责任人、优先级和计划完成时间时，每个接收人只收到一条汇总通知。
- 标题或正文由提出人修改、创建工单以及工单派生为逾期状态时不生成通知。
- 评论通知包含工单编号、标题、评论人和评论前 200 个字符；其他工单通知包含变更字段及新值。
- 超过摘要限制的内容截断，完整内容通过工单详情查看。
- 工单通知只进入站内通知，不投递飞书，不在飞书中展示或处理工单。
- 工单修改和对应站内通知必须在同一 PostgreSQL 事务中提交；通知写入失败时业务修改回滚。

## 飞书投递

- 飞书投递只适用于 `lease.expiring`。
- 事务提交后将发送任务投递给 Celery，最多重试 3 次。
- 飞书状态取值为 `pending`、`sent` 或 `failed`；无需投递时该字段为空。
- 飞书或 Redis 不可用不能撤销已经生成的站内通知。
- 不后台扫描失败通知，不提供手动重发。
- 不保存飞书请求和响应正文，只保存投递状态、有限失败原因和时间。

## Web 页面

- 顶部栏提供通知铃铛和未读数量；点击后打开右侧通知抽屉，不新增一级导航页面。
- 抽屉按未读优先、创建时间倒序展示，每页固定 50 条。
- 提供手动刷新和全部已读；不自动轮询。
- 单击通知后标记该通知已读，并跳转对应详情。
- 工单通知跳转 `/tickets/<id>`。
- 物理机通知跳转 `/resources?resource_id=<uuid>`，进入页面后打开对应详情。
- VM 通知跳转 `/virtual-machines?vm_id=<uuid>`，进入页面后打开对应详情。
- 资源已经释放、销毁或不可用时，目标页面展示当前状态或不存在提示，通知本身仍保留。
- 不提供通知删除、重发、渠道选择或通知偏好设置。
- 移动端通知抽屉占满可用宽度，文本必须自动折行且不能与操作区重叠。

## API

```text
GET   /api/v1/notifications
GET   /api/v1/notifications/unread-count
PATCH /api/v1/notifications/{id}/read
POST  /api/v1/notifications/read-all
```

- 所有接口要求登录，只能读取或修改当前用户自己的通知。
- 通知列表使用从 `1` 开始的 `page`，每页固定 50 条，响应使用项目统一分页契约。
- 标记已读是幂等操作；重复标记已读仍返回成功。
- 全部已读只修改当前用户当时已有的未读通知。

## 调度与清理

- `dev` 和 `prod` 各运行一个 Celery Beat，使用各自 Redis 和 PostgreSQL。
- Beat 每天 09:00 触发到期提醒扫描；扫描完成后清理创建超过 90 天的通知。
- Beat 调度时区为 `Asia/Shanghai`，每套环境使用独立持久化调度文件。
- Beat 不随 Worker 并发数扩容；同一环境同时只能运行一个实例。
- 错过当天 09:00 后不补跑，后续日期继续按正常计划提醒。

## 日志边界

- 通知不是审计日志、租约日志或任务事件。
- 创建通知、飞书投递、标记已读和全部已读不写入其他日志系统。
- 租约续期、释放和工单修改仍遵循各自原有记录规则。

## 验证

- 后端测试覆盖接收人规则、排除操作人、一次操作一条通知、每日去重、续期后重新提醒、
  90 天清理和飞书失败不影响业务。
- API 测试覆盖用户数据隔离、固定分页、单条已读和全部已读。
- 前端单元测试覆盖未读数量、标记已读、全部已读和详情跳转。
- 部署配置检查保证每套环境只有一个 Beat。
- 不增加真实飞书联调测试或 Playwright/E2E 测试。
